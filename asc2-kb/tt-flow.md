## 2. info.yaml (yaml_version 6)

Source: info.yaml in the template clone, and validation code project_info.py and project_checks.py in the tt-support-tools clone.

Fields under `project:`:
* `title`, `author`, `description`: must be non-empty strings.
* `discord`: optional.
* `language`: non-empty, for example "Verilog" or "SystemVerilog".
* `clock_hz`: required, must be an integer. 0 if not applicable. Used for the datasheet.
* `tiles`: one of the SKY130 sizes. Template comment: "Valid values: 1x1, 1x2, 2x2, 3x2, 4x2, 6x2 or 8x2". Format is WIDTHxHEIGHT.
  * The tools also accept 3x4, 4x4, 5x4, 6x4, 8x4, but the app calls 4-high "experimental" and may push it to a later shuttle. See tt-shuttle.md.
* `top_module`: must start with `tt_um_`. Template: "Make it unique by including your github username".
* `source_files`: files in ./src, "one per line". A `*` wildcard is rejected. Every file must exist.
  * Also update `PROJECT_SOURCES` in test/Makefile (template comment).
  * The top module must be defined in exactly one listed file (find_top_verilog in project.py).
* `analog_pins`: optional, default 0. Leave it out for a digital design.
* `yaml_version: 6`: "Do not change!". Any other value is an error.

Section `pinout:`:
* Keys ui[0..7], uo[0..7], uio[0..7] must all exist. "DO NOT delete or add any pins."
* At least one pin must have a non-empty name, or the docs check fails with "Please fill in the 'pinout' section".
* Extra keys are an error.
* It feeds the datasheet. Use names like REQ, ACK, IRQ, D0..D7.

## 3. src/config.json (LibreLane config)

Source: src/config.json in the template clone.

User-adjustable knobs (above the "DO NOT CHANGE ANYTHING BELOW THIS POINT" line):
* `PL_TARGET_DENSITY_PCT`: 60. "You can increase this if Global Placement fails with error GPL-0302. Users have reported that values up to 80 worked well for them."
* `CLOCK_PERIOD`: 20 (ns, so 50 MHz). "Increase this in case you are getting setup time violations."
* `PL_RESIZER_HOLD_SLACK_MARGIN`: 0.1, `GRT_RESIZER_HOLD_SLACK_MARGIN`: 0.05. Raise for hold violations.
* `RUN_LINTER`: 1, `LINTER_INCLUDE_PDK_MODELS`: 1. "Disabling the linter is not recommended!"
* `CLOCK_PORT`: "clk". For a second clock see the FAQ (needs your own SDC).

Fixed part (do not change):
* RUN_KLAYOUT_XOR 0, RUN_KLAYOUT_DRC 0, DESIGN_REPAIR_BUFFER_OUTPUT_PORTS 0, TOP/BOTTOM_MARGIN_MULT 1, LEFT/RIGHT_MARGIN_MULT 6, FP_SIZING "absolute", GRT_ALLOW_CONGESTION 1, FP_IO_HLENGTH/VLENGTH 2, FP_PDN_VPITCH 38.87, RUN_CTS 1, FP_PDN_MULTILAYER 0, MAGIC_DEF_LABELS 0, MAGIC_WRITE_LEF_PINONLY 1.

Generated by `tt_tool.py --create-user-config` (src/user_config.json, merged into src/config_merged.json):
* DESIGN_NAME = top_module, VERILOG_FILES = source_files, DIE_AREA from tile_sizes.yaml, FP_DEF_TEMPLATE = tt_block_<tiles>_pg.def, VDD_PIN VPWR, GND_PIN VGND, RT_MAX_LAYER met4.
  * Source: create_user_config in project.py and Sky130Tech in tech.py, tt-support-tools clone.
* So the project may route on met1..met4. met5 is not available to the project.

Timing constraints:
* The default LibreLane SDC sets input and output delay = CLOCK_PERIOD x IO_DELAY_CONSTRAINT / 100 on all IOs, a load of OUTPUT_CAP_LOAD on outputs, and a propagated clock.
  * Source: https://raw.githubusercontent.com/librelane/librelane/3.0.14/librelane/scripts/base.sdc, retrieved 2026-11-21 (saved at tt/librelane/base.sdc).
* IO_DELAY_CONSTRAINT and OUTPUT_CAP_LOAD come from the PDK defaults, not from the template.
  * Source: librelane/config/flow.py at tag 3.0.14 (`pdk=True`), retrieved 2026-11-21.
  * UNCERTAIN: the actual sky130A values. Read them from runs/wokwi/resolved.json in the GDS_logs artifact of your own run.
* The TT mux path delay outside the tile is not part of this STA. See tt-io.md.

## 5. SystemVerilog support and limits

* Default synthesis frontend in LibreLane 3.0.14 is `read_verilog -defer -sv` (Yosys built-in parser).
  * Source: librelane/scripts/pyosys/ys_common.py at tag 3.0.14, https://raw.githubusercontent.com/librelane/librelane/3.0.14/librelane/scripts/pyosys/ys_common.py, retrieved 2026-11-21.
* `USE_SLANG` (default False) switches to the slang frontend: "better SystemVerilog parsing capabilities but is not as battle-tested". `SLANG_ARGUMENTS` passes options.
  * Source: librelane/steps/pyosys.py at tag 3.0.14, retrieved 2026-11-21 (saved at tt/librelane/steps_pyosys.py).
  * It would be a new key in src/config.json. The template says not to edit that file "unless you know what you are doing". UNCERTAIN whether TT supports it. Untested.
* Yosys docs on the built-in frontend: "SystemVerilog packages are supported". Once a package is read, it is "available to SystemVerilog files being read into the same design afterwards". So list the package file first in source_files.
  * Not supported: nested packages (`import` inside a package), type casts, arrays of packed structs/unions, structure literals, unpacked array assignment, array literals, positional interface arguments. Enums are not strongly typed.
  * Supported: always_comb/always_ff/always_latch, logic, typedef, enum, packed struct/union, multidimensional arrays, unique/priority case and if, interfaces partially (named connection only).
  * Source: https://yosyshq.readthedocs.io/projects/yosys/en/latest/using_yosys/verilog.html, retrieved 2026-11-21. This is the latest Yosys docs, not the 0.55 or 0.62 docs.
* RISK: the port check uses yowasp-yosys 0.55 built-in parser even if USE_SLANG is set. The top module file (and what it needs) must parse there.
  * Source: check_ports in project.py, tt-support-tools clone.
* Safest for a one-day schedule: plain Verilog-2005 or a light SV subset (logic, always_ff, always_comb, localparam). Avoid packages if possible; if used, one package file, listed first, no casts.
* VHDL is transpiled with GHDL (`ghdl synth --std=08 --out=verilog`) if a source ends in .vhdl.
  * Source: transpile_vhdl in project.py, tt-support-tools clone.

## 6. Design rules (what fails the build or the submission)

Port and naming rules:
* Top module name starts with `tt_um_` and is unique.
  * Source: https://tinytapeout.com/hdl/important/, retrieved 2026-11-21; project_info.py.
* Exact port list: clk, ena, rst_n (1-bit inputs), ui_in[7:0], uio_in[7:0] (inputs), uo_out[7:0], uio_out[7:0], uio_oe[7:0] (outputs). Missing, wrong width, wrong direction, or any extra port is an error.
  * Source: check_ports in project.py, tt-support-tools clone; https://tinytapeout.com/hdl/important/.
* "All output pins must be assigned. If not used, assign to 0."
  * Source: src/project.v in the template clone.

RTL rules:
* No initial statements. "Initial statements are not allowed, so you must use an explicit reset." Flops power up random.
  * Source: https://tinytapeout.com/hdl/fpga_vs_asic/, retrieved 2026-11-21.
* Latches are not banned by TT. The memory page shows latch-based RAM (up to 512 bits per tile). Unintended latches are still a bug, and STA of latches needs care.
  * Source: https://tinytapeout.com/specs/memory/, retrieved 2026-11-21.
* LibreLane 3.0.14 defaults that stop the flow (none overridden by the template):
  * ERROR_ON_LINTER_ERRORS = True. ERROR_ON_LINTER_TIMING_CONSTRUCTS = True (delays and similar). ERROR_ON_LINTER_WARNINGS = False.
  * ERROR_ON_SYNTH_CHECKS = True: "combinational loops and/or wires with no drivers".
  * ERROR_ON_UNMAPPED_CELLS, ERROR_ON_NL_ASSIGN_STATEMENTS, ERROR_ON_TR_DRC, ERROR_ON_MAGIC_DRC, ERROR_ON_LVS_ERROR, ERROR_ON_DISCONNECTED_PINS, ERROR_ON_LONG_WIRE, ERROR_ON_PDN_VIOLATIONS = True.
  * KLayout DRC and XOR are switched off in the template (RUN_KLAYOUT_DRC 0, RUN_KLAYOUT_XOR 0); the precheck job runs its own KLayout checks.
  * Source: librelane/steps/checker.py at tag 3.0.14, retrieved 2026-11-21 (saved at tt/librelane/steps_checker.py).
  * Setup and hold violations: which corners cause an error is a PDK setting (TIMING_VIOLATION_CORNERS, `pdk=True`). UNCERTAIN which sky130 corners; the template comments assume setup and hold violations must be fixed.
* Check the Yosys warnings in the action summary: multiple drivers, unconnected nets, undriven outputs, combinational loops.
  * Source: https://tinytapeout.com/hdl/important/, retrieved 2026-11-21.
* Make sure the design is not optimised away. The tools warn below 20 cells for HDL projects.
  * Source: https://tinytapeout.com/hdl/important/; check_num_cells in project.py.
* Projects that look like crypto get a warning: "Due to US export restrictions, we may not be able to accept it."
  * Source: app bundle https://app.tinytapeout.com/_build/assets/index-DDvc-iK8.js, retrieved 2026-11-21.

## 7. Tests (cocotb)

Source: test/ folder in the template clone.
* test/tb.v instantiates the top module (rename `tt_um_example`). It dumps tb.fst. Under `GL_TEST` it adds VPWR=1 and VGND=0 power ports.
* test/test.py: cocotb test. Starts a 10 us clock (100 kHz), sets ena=1, ui_in=0, uio_in=0, holds rst_n=0 for 10 cycles, then checks outputs.
* test/Makefile: SIM=icarus, TOPLEVEL=tb, COCOTB_TEST_MODULES=test, PROJECT_SOURCES=project.v (edit this). `-I src` is on the include path.
  * GL mode (`make GATES=yes`): adds -DGL_TEST -DFUNCTIONAL -DUSE_POWER_PINS -DSIM -DUNIT_DELAY=#1, the sky130_fd_sc_hd primitives, and test/gate_level_netlist.v.
* CI checks results with `python -m cocotb_tools.check_results results.xml` (make alone returns success even on failure).
* The GL test runs the same test.py on the post-layout netlist in CI. A testbench that peeks at internal RTL signals will fail in GL mode.
  * Source: gl_test/action.yml in the tt-gds-action clone; https://tinytapeout.com/hdl/testing/, retrieved 2026-11-21.
* cocotb 2.x API is used (`Clock(dut.clk, 10, unit="us")`, `cocotb_tools`). Old cocotb 1.x examples need small edits.

## 10. Tile size and capacity on SKY130

* 1x1 tile die area: 161.00 x 111.52 um (about 17,955 um2).
  * Source: tech/sky130A/tile_sizes.yaml, tt-support-tools clone. This is the DIE_AREA the flow uses.
  * The template comment says "A single tile is about 167x108 uM". It does not match tile_sizes.yaml. Trust tile_sizes.yaml.
* Multi-tile sizes include the channel between tiles, so they grow faster than tile count:
  * 1x2 = 161.00 x 225.76, 2x2 = 334.88 x 225.76, 3x2 = 508.76 x 225.76, 4x2 = 682.64 x 225.76, 6x2 = 1030.40 x 225.76, 8x2 = 1378.16 x 225.76 um.
  * 8x2 area is about 311,000 um2, about 17.3 times a 1x1.
  * Source: tech/sky130A/tile_sizes.yaml.
* Cells: "One tile holds approximately 1000 standard cells" (cells_per_tile: 1000).
  * Source: docs/product/facts.yaml and datasheet.yaml in the tt-support-tools clone.
  * FAQ (TT04-TT10 era): "about 160x100 um. This is enough for about 1000 digital logic gates". Source: https://tinytapeout.com/faq/#how-big-can-my-design-be, retrieved 2026-11-21.
* Flip-flops: "you can fit about 320 DFFs (40 bytes of memory) in a single tile", less once logic is added. A 264-DFF RAM used 70% of a tile.
  * Source: https://tinytapeout.com/specs/memory/, retrieved 2026-11-21.
* Utilization: target density 60% by default. Up to 80% reported to work (config.json comment). The FAQ says "around 62%" has worked; otherwise buy another tile.
  * Source: src/config.json; https://tinytapeout.com/faq/#why-is-target-density-set-to-60-should-i-change-it-to-100-or-should-i-add-another-tile, retrieved 2026-11-21.
* You can try tile sizes without buying: change `tiles` in info.yaml and see if the GDS action passes.
  * Source: https://tinytapeout.com/faq/#my-gds-action-is-taking-much-longer-than-usual, retrieved 2026-11-21.

ESTIMATE (mine, not from TT), for sizing the 32-bit CPU:
* Scale the 320-DFF-per-tile rule by area: 8x2 holds very roughly 5,000 DFF-equivalents, 4x2 about 2,500.
* A register file of N x 32 bits in flops costs N x 32 DFFs plus read muxes. 16 registers = 512 DFFs; 32 registers = 1024 DFFs, about 3 tiles of flops before any logic.
* A 32-bit datapath plus control plus a flop register file will most likely need 4x2 to 8x2. Run the GDS action at the target size early.

## 11. First-time submitter checklist (must not miss)

* Use the SKY template (sky130A). Do not reuse a GF or IHP repo.
* Fill info.yaml fully: title, author, description, language, clock_hz (integer), tiles, top_module, source_files, pinout (all 24 keys present, at least one named).
* Update test/Makefile PROJECT_SOURCES and test/tb.v module name.
* docs/info.md: replace both placeholder sections, or the docs check fails ("Missing 'How it works' section", "Missing 'How to test' section").
  * Source: check_info_md in project_checks.py, tt-support-tools clone.
  * Images in docs/: "Each image must be less than 512 kb in size, and the combined size of all images must be less than 1 MB."
  * Source: docs/info.md in the template clone.
* Analog is not needed. Do not set analog_pins. Do not use the analog template. Analog pins are only charged if used.
  * Source: calculator bundle (analog pin line only when analogPins > 0), https://app.tinytapeout.com/_build/assets/invoice-D4MX0I-B.js, retrieved 2026-11-21.
* Power: no power ports in RTL. The flow adds VPWR/VGND. TT power-gates each project; it is powered only while selected. Core supply 1.8 V (sky130 tt corner `nom_tt_025C_1v80`).
  * Source: tech.py (Sky130Tech.tt_corner), tt-support-tools clone; power gating details in tt-io.md.
* Clock: template default 50 MHz (CLOCK_PERIOD 20 ns). IO pads limit about 66 MHz in, 33 MHz out (see tt-io.md). The FAQ for TT04-TT10 says top clock "At least 50MHz".
  * Source: src/config.json; https://tinytapeout.com/specs/clock/; https://tinytapeout.com/faq/#what-is-the-top-clock-speed, retrieved 2026-11-21.
* Always reset explicitly. ena is 1 whenever the design is powered (template comment).
* Enable Actions and GitHub Pages on the repo before the first push of real work.
* Keep the copyright header and Apache-2.0 notice correct; respect licenses of any reused code.
  * Source: https://tinytapeout.com/faq/#how-do-i-correctly-attribute-authorship-for-a-project, retrieved 2026-11-21.
* Leave time: GDS runs get long for big designs, tt-support-tools main can change, and only the last revision before 2026-11-30 20:00 UTC counts.
* Help: Discord, https://discord.gg/rPK2nSjxy8 (FAQ link), retrieved 2026-11-21.

## 12. The local run on this Mac (2026-11-22)

## 14. The whole chip at three sizes (2026-11-22)

`make harden TILES=...` in [asc2-targets/tiny-tapeout/](../asc2-targets/tiny-tapeout/) ran the official flow on the whole chip: the CPU, the MMU, the three devices, the bus unit, and the filters. Each run takes about 13 minutes on this Mac, two of them side by side.

What each size gave:

* 4x2 (8 tiles, 149,183 um2 of core): does not fit. The cells take 72.5 percent of the area before the routing. The global routing ends with congestion (86 percent of the tracks of metal 1 and 2 taken, 1,251 places with more wires than tracks), and the detailed routing starts with 24,559 violations, against about 9,000 for the sizes that end with none. The run was stopped there.
* 6x2 (12 tiles, 225,802 um2 of core): fits. 48.2 percent of the area is cells; `tt_tool.py --print-stats` gives 42.7 percent, which leaves out the tap cells. 0 DRC errors (Magic and the router), LVS clean, 0 antenna violations, no setup and no hold violation in any corner. 406,783 um of wire.
* 8x2 (16 tiles, 302,420 um2 of core): fits. 36.5 percent of the area is cells (31.9 percent by `--print-stats`). The same checks are clean. 457,564 um of wire.

The cells of the 6x2 run, 108,834 um2 in all, without fill cells:

* 1,343 flip-flops, 28,566 um2.
* Logic, 52,540 um2.
* 2,045 buffers that the tools added for timing, 19,897 um2. 1,073 of them are for hold and none for setup.
* Clock buffers, 2,791 um2. Tap cells and 55 antenna diodes are the rest.

Where the logic and the flip-flops are, from a run of Yosys 0.71 and ABC with the same cell library, before any buffer (68,400 um2 in all): the register file 14,600; the CPU 18,400; the eight translations 13,300; the bus unit 7,200; the chain of `dot4` 5,700; the ALU 2,400; the timer 1,500; the keyboard receiver and its controller 1,500; the interrupt controller 900; the rest 2,700. The estimate before the chip was written was 142,000 to 158,000 um2 of cells.

Timing:

* The tools work for the slowest corner (100 C, 1.60 V), and they make a path only as fast as the clock period asks. The runs above asked for 40 ns. Later runs of the chip in its last form, at 6x2, asked for three periods:
    * 20 ns: the longest path takes 12.0 ns in the typical corner and 22.7 ns in the slowest one. The typical corner has 8.0 ns to spare and the fast corner 10.8 ns; the slowest corner misses by up to 2.7 ns, with 341 paths too slow in it. 111,597 um2 of cells.
    * 40 ns: the longest path takes 40.5 ns in the slowest corner, a miss by 0.5 ns. An earlier form of the chip met the same period by 1.1 ns. This is noise around zero.
    * 50 ns: the longest path takes 40.5 ns again, so 9.5 ns are to spare in the slowest corner and 30.3 ns in the typical one. From 40 ns up the chip has the cells of its slowest form. 111,277 um2 of cells.
* The area is the same at every period, and a shorter period gives a faster chip. [config.json](https://github.com/toksaitov/ttsky26e-almurut2/blob/main/src/config.json) therefore asks for 20 ns, the period of the template: the chip is about twice as fast as with 40 ns, and its report shows setup violations in the slowest corner. They do not matter at the clock that the RP2040 gives, 12.5 MHz on the bench, a period of 80 ns.
* The last official run (6x2, 20 ns): 13,042 cells, 111,597 um2, 49.4 percent of the area (43.7 percent by `--print-stats`), 426,303 um of wire, 0 DRC errors, LVS clean, 0 antenna violations, no hold violation.
* Hold: the smallest slack is 0.104 ns, in the fast corner, after the 0.25 ns of clock uncertainty that the flow's own constraints subtract. It is the same at every period.
* Settings that were tried for 20 ns in the slowest corner, all worse than the default: `SYNTH_STRATEGY` set to `DELAY 1` (a miss by 6.9 ns) and to `DELAY 4` (4.9 ns); `SYNTH_ADDER_TYPE` set to `CSA` (3.6 ns); the same with `SYNTH_SIZING` and `SYNTH_ABC_BUFFERING` (3.5 ns). The longest paths start at the state of the CPU, go through the adder of the ALU, and end in the trap record (`cr1`, `cr2`, `cr5`) and in the translations. 20 ns in the slowest corner needs a change of the hardware description, not of a setting. (Section 16 has what was tried after this.)

Warnings that stay, in every run:

* Slew: 820 pins in the typical corner and 5,052 in the slow corner of the 6x2 run at 40 ns have an edge slower than the limit of 0.75 ns; the last run at 20 ns has 654 and 4,489. Most are between 0.75 and 2 ns; the slowest is under 3 ns, in the slow corner. They are long wires behind small cells: the block is 1.0 to 1.4 mm wide and the longest wire is 0.78 mm. The timing numbers above include these edges.
* Capacitance: 29 pins over the limit in the slow corner. Fanout: 106 nets with more than 10 loads.
* Setup and hold are checked with the flow's generic constraints; no constraint file of our own exists (`PNR_SDC_FILE`, `SIGNOFF_SDC_FILE`).
* Yosys: "Replacing memory words_q with list of registers", which is what the register file is meant to be.
* The flow's estimate of power is 7 mW at 25 MHz.

A finding on the way: the register file was written as `words_q[waddr] <= wdata` with 12 words and a 4-bit address, and Yosys built 16 words, 512 flip-flops, for it. With an enable per word it builds 12, and the chip lost 128 flip-flops and about 4,500 um2. A simulation of the routed gates and the same runs through the GitHub action of the template came later, and both passed: the GitHub run on 2026-11-25.

## 15. What 4 GB of physical addresses cost (2026-11-23)

The machine got 4 GB of physical addresses in place of 16 MB ([machine-contract.md](machine-contract.md), "32-Bit Physical Addresses"). The chip got a fourth address byte in the bus unit, eight more bits in each of the eight translations, and eight more bits in the register of the top page table. The same official run at 6x2 with 20 ns, before and after:

* Cells: 13,042 before, 13,249 after, 207 more. 88 of them are flip-flops (1,347 and 1,435).
* Area of the cells: 111,597 um2 before, 114,800 um2 after, 3,203 um2 more, which is 2.9 percent.
* Share of the 6x2 area: 49.4 percent before, 50.8 percent after. The number of tiles does not change, and the chip is as far from 4x2 as it was.
* Wire: 426,303 um before, 444,441 um after.
* 0 DRC errors, LVS clean, 0 antenna violations, and no hold violation, as before.
* The longest path in the slowest corner: 22.7 ns before, 23.7 ns after, which is 42 MHz in the slowest corner in place of 44 MHz; the typical corner is unchanged at 12 ns. The other layouts of section 16 differ from each other by more than this 1 ns, so it is not shown that the wider addresses are the cause.

On the bus a request that carries an address is one byte longer: nine bytes for the write of a word in place of eight. A fetch of the next instruction carries no address and costs what it did.

## 16. The tries for 50 MHz in the slowest corner (2026-11-23)

A few tries were made to have the chip sure at 50 MHz, to be dropped if they cost too much work, code, area, or safety. The tries below are layout runs of the chip with 4 GB of addresses at 6x2 and 20 ns; the number is the miss of the longest path in the slowest corner (100 C, 1.60 V, the slowest wires).

* The settings as they are: 3.7 ns.
* The delay cells kept out of the buffering (`EXTRA_EXCLUDED_CELLS`): 4.7 ns. The tools use delay cells as buffers on nearly every slow path, and without them the tools pick other slow cells.
* The same and a second repair of the timing after the first routing (`RUN_POST_GRT_DESIGN_REPAIR`, `RUN_POST_GRT_RESIZER_TIMING`, with margins): 3.4 ns.
* Two changes of the hardware description (the user stack pointer read as a control register without the multiplexer of the register file, and the translations read by an OR of the matching entry in place of a choice by its number), with the settings as they are: 4.8 ns.
* The two changes and the settings of the third line: 4.8 ns.

A run repeated with nothing changed gives the same layout and the same numbers. The five layouts above span 23.4 to 24.8 ns; the best of them gains 0.3 ns and the others lose up to 1.1 ns, with no pattern, so no try is a gain worth its risk, and none was kept: [config.json](https://github.com/toksaitov/ttsky26e-almurut2/blob/main/src/config.json) and the hardware description are as they were. In the layout that is kept, the 317 slow paths of the slowest corner start at three registers: 153 at the register with the kind of the memory access, 118 at the state of the CPU, and 46 at the instruction register; the slowest one goes from the instruction register to the overflow flag. All of them have the same shape: a register is decoded into the choice of the operands or of the address, the result passes the adder of the ALU or the comparison of the translations, and it is stored, all in one clock. To be sure of 20 ns the CPU would have to decode a clock ahead and keep the choices in registers, which changes the heart of a CPU that every test has passed; that is not a small try, and it was not done.

What the chip does, then: in the typical corner the longest path takes about 12 ns (80 MHz). In the slowest corner it takes 23.7 ns in the layout that is kept (42 MHz), and up to 24.8 ns in the tries. The number to promise is 37.5 MHz, a clock that the RP2350 can make from 150 MHz, with a little room. The bench runs at 12.5 MHz, and the bus to the RP2350, not the chip, sets the speed of the whole machine.

## 17. What the registers on the debug port cost (2026-11-24)

The debug port shows every register, 640 bits in place of 128. The counter of the port got two more bits, a selector reads the twelve words of the register file and `cr1` to `cr4`, and the selected bit goes to its pin through a flop. Nothing can write through the port, and no line of the CPU's control changed. The same official run at 6x2 with 20 ns, before and after:

* Cells: 13,249 before, 13,791 after, 542 more. 4 of them are flip-flops (1,435 and 1,439).
* Area of the cells: 114,800 um2 before, 120,353 um2 after, 5,553 um2 more, which is 4.8 percent.
* Share of the 6x2 area: 50.8 percent before, 53.3 percent after. The number of tiles does not change.
* Wire: 444,441 um before, 513,106 um after. The selector takes a wire from each of 512 flops to one place.
* 0 DRC errors, LVS clean, 0 antenna violations, and no hold violation, as before.
* The longest path in the slowest corner: 23.7 ns before, 24.5 ns after, which is 41 MHz in place of 42 MHz; in the typical corner 12.2 ns before and 12.7 ns after. The layouts of section 16 differ from each other by more than this, so it is not shown that the selector is the cause; the wires of the selector load the flops of the registers, which would explain it.

A first try without the flop before the pin had the selector as the longest path of the chip: from the counter through 640 inputs to the pin, 15.5 ns in the typical corner. The pin is read by the RP2040 many clocks after it asks, so the path did no harm, but it hid the real longest path in the reports, and that layout was 2,000 um2 larger. With the flop the bit is at the pin four clocks after a rise of the port's clock; the firmware waits twelve.
